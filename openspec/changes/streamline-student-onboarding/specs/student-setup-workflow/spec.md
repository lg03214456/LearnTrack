## Purpose

Provide one continuous, recoverable setup journey for creating a student, choosing classes, assigning learning materials and configuring personal examination coverage. Make later maintenance available directly from the student profile without changing existing authorization, learning history or completion calculations.

## ADDED Requirements

### Requirement: Continuous student setup dialog
The system SHALL offer the ordered steps basic information and classes, material assignment, and personal examination coverage in one responsive dialog without navigating away between steps. A student MUST be successfully created before dependent writes occur, and the assigned student number MUST remain generated by the existing server workflow.

#### Scenario: New student setup
- **WHEN** an authorized operator saves valid basic information and permitted class selections
- **THEN** the system shows the saved student identity and number, advances to material setup in the same dialog, and uses that identity for all subsequent steps

### Requirement: Independent durable saves and safe cancellation
Each step SHALL save independently and clearly distinguish unsaved input from saved records. Operators MUST be able to save and continue or defer optional later setup. Closing after a successful step MUST retain saved records and MUST NOT delete or recreate a student, enrollment, plan or range.

#### Scenario: Defer after student creation
- **WHEN** the operator creates a student and selects later setup instead of assigning materials
- **THEN** the student and saved class selections remain and the profile provides a continuation entry

#### Scenario: Back navigation and uncertain results
- **WHEN** the operator returns to a saved step or a transport/audit failure leaves a save outcome uncertain
- **THEN** the system uses update semantics with the saved identity and revision where known, or asks the operator to reload and confirm records before retrying creation
- **AND** it does not automatically repeat a create operation or claim that a later failure rolled back prior steps

### Requirement: Material and examination dependency handling
Material setup SHALL use only permitted published versions and existing plan replacement rules. Examination setup MUST load the student's authoritative assigned content after material saving, not unsaved template selections. Missing materials, missing permissions or unavailable examination storage MUST have explicit explanatory states and an option to finish saved setup without fabricating success.

#### Scenario: Continue to examination coverage
- **WHEN** material assignment succeeds and the operator continues
- **THEN** personal range setup presents content from the saved student's plans without leaving the dialog or including another student's materials

#### Scenario: Existing plan replacement
- **WHEN** the operator chooses material that would replace an existing same-term same-subject plan
- **THEN** the system explicitly explains and confirms the existing replacement behavior before saving and preserves completed history according to the existing rules

### Requirement: Setup completion and another student
The system SHALL provide a completion summary, a link to the saved student's profile, and an action to create another student. Starting another student MUST reset transient inputs and dependent identities without deleting the previous student's saved data.

#### Scenario: Create the next student
- **WHEN** the operator finishes or defers setup and chooses to add another student
- **THEN** a fresh basic-information step opens with no previous name, classes, material selection or examination range carried forward

### Requirement: Resume and truthful setup indicators
The student profile SHALL show class membership, material and range setup states using authoritative data, and provide direct edit or continuation controls to permitted users. No classes or no exam range MUST be displayed as not set, not an error. Unavailable data and inaccessible operations MUST NOT be mislabeled as missing configuration.

#### Scenario: Resume an existing student
- **WHEN** an authorized operator opens a previously created student's setup
- **THEN** saved data are preloaded, the student is not recreated, and the operator can change only the relevant step

### Requirement: Daily operations before history
The student progress page SHALL present examination coverage progress before current learning plans and keep non-active plans in a clearly labeled, initially collapsed history section. History MUST remain readable with original version and status labels, and MUST NOT regain mutation controls simply because it is expanded.

#### Scenario: Current and historical plans coexist
- **WHEN** the student has an active plan and replaced, archived or completed plans
- **THEN** active plans are immediately visible, historical plans are available by expansion, and coverage and existing progress calculations remain unchanged

### Requirement: Scoped and accessible interactions
The workflow SHALL enforce each operation's existing server-side permission, tenant and student scope; saved identifiers from the client MUST be revalidated. Read-only users and Platform Owner inspection MUST NOT gain tenant writes. The dialog MUST support labels, keyboard navigation, focus return, one active modal, pending protection and contained narrow-screen content.

#### Scenario: Scope or session changes
- **WHEN** the operator switches student/organization or loses authorization during setup
- **THEN** previous transient student data are cleared or hidden, pending responses cannot populate the new context, and unauthorized further writes are refused

#### Scenario: Pending save and cancel
- **WHEN** a step is saving
- **THEN** duplicate submission and dismissal are blocked until the result is known, with an accessible pending indication and safe error handling

### Requirement: Preserve existing entry points and domain behavior
Independent student editing, class roster inspection, class/session navigation, assessments, personal ranges and existing plan actions SHALL remain usable. The new journey MUST NOT create authentication accounts automatically, change score or completion formulas, automatically assign materials from class membership, or fall back to mock data when persistence fails.

#### Scenario: Existing daily actions
- **WHEN** staff use the original profile, roster, lesson or assessment entry points
- **THEN** scope, save behavior and history retention remain compatible while the new setup shortcuts avoid unnecessary page changes
